## D-001 — 외부 협업은 GitHub Private Repository와 HTTPS를 사용

- date: 2026-07-21
- decision: 팀원 담당자가 GitHub에 Private Repository를 만들고, 팀원은 HTTPS로 각자 clone·pull·push한다.
- alternatives: Obsidian Sync, Obsidian Publish, SSH 접속
- reason: 해커톤 장소가 외부이고 각 팀원의 로컬 에이전트가 Markdown 파일에 직접 접근해야 하며, SSH 서버 의존성을 없애기 위해서다.
- evidence: `REMOTE_SETUP.md`, 로컬 Git 저장소의 `main` 기준본
- tradeoff: 실시간 공동 편집은 아니며, 같은 파일을 동시에 수정하면 Git 충돌이 생길 수 있다.
- owner: 팀
- status: active

## D-002 — 캐릭터견은 가상견, 실제 보호견은 추천으로 연결

- date: 2026-07-21
- decision: 유저가 키우는 캐릭터견은 지속적으로 존재하는 가상견으로 하고, 유저가 성격·행동 특성을 설정하면 AI 페르소나를 부여한다. 실제 보호견은 게임 캐릭터가 아니라 성향 기반 추천 카드/콘텐츠로 연결한다. *(초안의 "위치 기반"은 D-018에서 철회)*
- alternatives: 실제 보호소 보호견 1마리를 그대로 게임 캐릭터로 사용 (PRD v0.9의 전제)
- reason: 실제견은 보호 기간이 짧고 안락사·입양으로 캐릭터가 갑자기 사라질 수 있다. 보호견별 캐릭터·콘텐츠 제작은 보호소와 팀 모두에게 비용·시간상 비현실적이다.
- evidence: `PRD.md` v1.0 §4.1, §4.3
- tradeoff: "실존 개를 키운다"는 v0.9의 정서적 훅은 약해진다. 대신 추천 카드·후원 폐루프로 실제견과의 연결을 유지한다.
- owner: 팀
- status: active

## D-003 — 서비스 핵심은 참여 장벽의 단계적 완화

- date: 2026-07-21
- decision: 사용자를 바로 입양으로 유도하지 않고, 게임 → 관심 → 학습 → 소액 후원 → 물품 후원 → 방문 → 봉사 → 임시보호 → 입양 퍼널에서 각자 상황에 맞는 다음 한 걸음만 AI가 추천한다. 개인화는 선택형+자유 서술 설문과 플레이 데이터를 LLM이 분석하는 방식으로 한다.
- alternatives: 입양 매칭 중심 설계 (v0.9), 단순 선택형 설문
- reason: 핵심 문제를 "관심은 있지만 시간·거리·정보 부족으로 행동하지 못하는 사람들의 참여 장벽"으로 재정의했다. 입양은 책임이 필요한 행동이므로 장벽을 낮추지 않고 교육적 안내를 제공한다.
- evidence: `PRD.md` v1.0 §1.1, §4.4
- tradeoff: 성공 지표가 입양 건수 단일 지표에서 퍼널 단계별 전환율로 분산되어 계측이 복잡해진다.
- owner: 팀
- status: active

## D-006 — 미니게임은 최소 3종, 완성되는 대로 순차 추가 (D-004 대체)

- date: 2026-07-21
- decision: 미니게임을 최소 3종으로 목표를 잡는다. 단 동시에 만들지 않고 MG1(3매치)을 완성도 있게 구현한 뒤 완성되는 대로 MG2·MG3을 붙인다. MG2·MG3의 장르(산책 리듬게임, 간식 타이밍게임)는 후보이며 MG1 완성 시점에 재검토한다. 게임별 지급 포인트는 차등 가능.
- alternatives: D-004의 3매치 1종 집중, 3종 동시 개발
- reason: 1종만으로는 유저가 질린다. 반대로 저품질 3종 동시 개발은 D-004에서 이미 배제한 실패 경로다. "최소 3종 목표 + 순차 완성"이 두 요구를 모두 만족한다.
- evidence: `PRD.md` v1.0 §4.2, §4.5
- tradeoff: 해커톤 범위에서는 MG1만 나온다. 3종 구조는 로드맵 약속으로 남으므로 발표 시 "구현 완료"와 "설계 확정"을 구분해 말해야 한다.
- owner: 팀
- status: active

## D-007 — 발바닥은 미니게임 입장에만 소모, 돌봄은 무료

- date: 2026-07-21
- decision: 발바닥(행동력)은 MG1~MG3 미니게임 입장 시에만 1개씩 소모한다. 밥 주기·산책·교감 등 돌봄 행동은 발바닥을 소모하지 않는다.
- alternatives: 돌봄과 미니게임이 발바닥을 공용으로 소모 (PRD v0.9 방식)
- reason: 돌봄에 진입 장벽을 두면 애착 형성과 매일 접속의 이유가 함께 깎인다. 발바닥의 본래 역할은 재화 획득 속도 상한과 어뷰징 방어이며, 그 대상은 미니게임이다.
- evidence: `PRD.md` v1.0 §4.1, §4.2
- tradeoff: 돌봄이 무제한이 되므로 돌봄 기반 지표(일일 돌봄 완료율)의 어뷰징 내성이 낮아진다. 성장 곡선 설계에서 별도로 다룬다.
- owner: 팀
- status: active

## D-008 — 전 연령 타깃 (10~20대 ~ 40~60대)

- date: 2026-07-21
- decision: "강아지를 좋아하는 사람"을 전제로 전 연령을 타깃한다. 키울 역량이 상대적으로 부족한 10~20대부터, 실질적인 비용 지불이 가능한 40~60대까지 포함한다. 연령은 참여 게이트가 아니라 AI 추천의 입력값으로 쓰며, 연령대별로 우선 추천되는 참여 방식이 다르다.
- alternatives: 20~30대 단일 타깃 (PRD v0.9)
- reason: 참여 방식이 후원·봉사·임보·입양으로 넓어지면서 연령대별로 가능한 기여가 달라졌다. 10~20대는 시간과 게임 친숙도를, 40~60대는 경제적 여건을 제공한다.
- evidence: `PRD.md` §3
- tradeoff: 단일 타깃 대비 UX 톤과 게임 난이도 설계가 어려워진다. 미성년 이용자 정책(결제·개인정보)이 반드시 들어가야 한다.
- owner: 팀
- status: amended by D-014 (연령을 AI 추천 입력값으로 쓴다는 부분은 폐기)

## D-009 — 돌봄 행동 7종 확장, 캐릭터견 레벨과 방치 하락

- date: 2026-07-21
- decision: 돌봄 행동을 7종(밥·목욕·똥 치우기·빗질·산책·원반던지기·교감)으로 확장한다. 캐릭터견은 레벨을 가지며 방치하면 레벨이 하락한다. 단 4개 조건을 반드시 함께 건다 — 유예 72시간, 하루 최대 1레벨, 성장 단계별 하한(획득물 회수 없음), 질병·부상·죽음·떠남 연출 금지.
- alternatives: 방치 페널티 없음, 컨디션 악화 연출로 압박
- reason: 배변 처리·위생 관리는 반려 생활에서 가장 자주 하지만 입양 상담에서 잘 다뤄지지 않는다. 게임에 넣으면 설계 원칙 4(입양을 서두르게 하지 않는다)와 준비 상태 판단에 실제 근거가 생긴다. 방치 하락은 리텐션 장치이되, 4개 조건 없이는 설계 원칙 2 위반이 된다.
- evidence: `PRD.md` §4.1
- tradeoff: 복귀 유저에게 레벨 하락은 부정적 경험이다. 복귀 3일 경험치 보너스와 재회 연출로 완화하며, 푸시 문구에 죄책감 유발 표현을 금지한다.
- owner: 팀
- status: active

## D-010 — 재화는 발바닥·포인트·육포 3종, 전환은 전부 단방향 *(명칭은 D-022로 대체 — 포인트 → 뼈다귀)*

- date: 2026-07-21
- decision: 발바닥(미니게임 입장 전용), 포인트(기본 재화), 육포(과금) 3종으로 고정한다. v0.9의 "사료 재화"는 포인트의 사용처로 흡수한다. 전환은 육포→포인트, 육포→발바닥만 허용하고 역방향은 전부 막는다. 포인트 획득의 주 경로는 캐릭터견 레벨업이다.
- alternatives: 사료 재화 별도 유지, 포인트→발바닥 허용, 포인트→육포 환전 허용
- reason: 포인트→육포를 막는 이유는 환금성 차단이다(실물 기부 재원과 얽히면 금전 사고 영역). 포인트→발바닥을 막는 이유는 `포인트→발바닥→미니게임→포인트` 루프가 닫혀 무한 인플레이션이 되기 때문이다. 레벨을 포인트 획득의 주 경로로 두면 방치 시 획득량이 자연히 줄어, 개를 아프게 하는 연출 없이 방치에 비용이 생긴다.
- evidence: `PRD.md` §5
- tradeoff: 무과금 유저의 포인트 획득 속도가 레벨에 종속되어 초반 체감이 느릴 수 있다. 밸런스 시트에서 초반 곡선을 완만하게 잡는다.
- owner: 팀
- status: active

## D-011 — 후원 재원은 과금에서 나온다 (판매 연동 기부)

- date: 2026-07-21
- decision: 후원의 실제 재원을 브랜드 CSR 예산이 아니라 **과금**(스킨 판매, 실물 옷+스킨 세트 판매, 육포 판매 적립분)으로 삼는다. 상품마다 판매 연동 기부 목표를 붙여 판매량이 브랜드 구호 집행을 트리거하게 한다. 포인트는 재원이 아니라 "모인 재원을 어디에 쓸지 정하는 분배 권한"으로 정의한다. 동기 분배 원칙은 **돈은 재원을, 시간은 명예를 만든다** — 랭킹·기부 증서 명의는 과금 유래 포인트를 제외해 산정한다.
- alternatives: 브랜드 CSR 예산 선집행 구조(초안), 포인트를 모금액처럼 표기
- reason: CSR 예산 의존은 협찬이 끊기면 약속이 무너지고, 유저에게 "내가 뭘 해서 저게 됐는지" 인과가 보이지 않는다. 판매 연동은 브랜드 쪽 예산 승인이 쉽고 집행 증빙이 판매 실적과 함께 나온다. 게임 속 캐릭터견이 입은 옷이 실제로 보호견에게 가는 구조는 스킨 구매와 후원을 같은 동작으로 만든다.
- evidence: `PRD.md` §6.1~6.3, §7.1
- tradeoff: 재원이 매출에 연동되므로 판매 부진 시 기부 규모가 줄어든다. 미달성 캠페인도 결과를 공개하고, 실제 집행이 없는 구간은 "모의 기부" 라벨을 유지한다.
- owner: 팀
- status: active

## D-012 — 보호소·브랜드는 페르소나가 아니라 구조로 정의한다

- date: 2026-07-21
- decision: 대상 사용자(§3)에서 "보호소 직원"과 "후원 브랜드" 페르소나를 삭제한다. 보호소는 후원을 받는 대상이므로 §6 후원 구조에서, 브랜드는 협업 대상이므로 §7 커머스 구조에서 각각 "무엇을 주고받고 어떤 절차로 도는지"로 명세한다. 보호소를 지칭할 때는 개인(직원)이 아니라 기관(보호소)으로 쓴다.
- alternatives: 4개 페르소나 유지 (PRD v0.9~v1.0)
- reason: 페르소나로 두면 "동기"만 서술되고 실제 절차가 비어 있게 된다. 보호소가 실제로 하는 일(등록 1회 + 수령 확인 1건)과 브랜드가 주고받는 것(상품 공급·판매 연동 약정 ↔ 노출·집행 증빙)을 구조로 적어야 구현 가능한 명세가 된다.
- evidence: `PRD.md` §3, §6, §7
- tradeoff: 대상 사용자 섹션이 플레이어 한 종류로 단순해져, 발표에서 이해관계자 다양성을 별도로 설명해야 한다.
- owner: 팀
- status: active

## D-013 — "유기견" 대신 "보호견"으로 용어 통일

- date: 2026-07-21
- decision: 제품의 모든 표기에서 "유기견"을 쓰지 않고 "보호견"으로 통일한다. 문서·게임 UI·AI 프롬프트·푸시 문구·발표 자료가 모두 해당된다. 유일한 예외는 국가 통계의 공식 명칭("유실·유기동물")을 인용할 때이며, 이 경우도 인용임이 드러나게 표기한다.
- alternatives: "유기견" 유지 (검색량·인지도 우위)
- reason: "버려진 개"라는 과거형 낙인 대신 "지금 보호받고 있는 개"라는 현재 상태로 부르는 것이 설계 원칙 1(소유가 아니라 참여)과 추천 톤에 맞는다.
- evidence: `PRD.md` 문서 상단 용어 원칙, 부록 A
- tradeoff: "유기견"이 대중 인지도와 검색량에서 우위이므로, 외부 마케팅·SEO에서는 병기 전략을 따로 검토해야 한다.
- owner: 팀
- status: active

## D-014 — 연령은 AI 추천 입력에서 제외한다 (D-008 일부 대체)

- date: 2026-07-21
- decision: 연령대별로 게임 내용을 다르게 만들지 않고, AI 추천의 입력값에서도 나이를 제외한다(설문에 넣지 않고 LLM 프롬프트에도 전달하지 않는다). §3 대상 사용자 표는 "누가 우리 앱을 쓰는가"에 대한 설명일 뿐 기능 명세가 아니다. 유일한 예외는 결제 관련 법적 요건(미성년자 법정대리인 동의·결제 한도)이며 이는 개인화가 아니라 준법 사항이다.
- alternatives: D-008의 "연령을 AI 추천 입력값으로 사용" 안
- reason: 설문이 이미 주거·시간·경제력·경험 등 실제 여건을 직접 묻고 있으므로 나이는 중복된 대리 지표다. 대리 지표로 판단하면 연령 편견이 그대로 추천에 실린다 — 여건이 되는 20대는 입양을, 시간이 없는 50대는 후원을 추천받아야 한다.
- evidence: `PRD.md` §3, §4.3
- tradeoff: 연령 기반의 손쉬운 세분화를 포기하므로, 설문의 자유 서술 품질이 추천 정확도를 좌우한다. 설문 문항 설계 비중이 커진다.

- status: superseded by D-016 (나이를 추천 입력에 포함하기로 번복)

## D-016 — 설문은 온보딩 1회, 추천 엔진은 하나 (D-014 번복 포함)

- date: 2026-07-21
- decision: 개인화 설문을 **서비스 최초 진입(캐릭터견 생성) 시점에 1회** 받는다. 이 설문으로 견종 3개를 추천하고 유저가 그중 하나를 고른다. **보호견 추천 시점에는 설문을 다시 받지 않고 같은 설문을 재사용**한다. 견종 추천과 보호견 추천은 별도 기능이 아니라 **하나의 추천 엔진**에서 시점만 달리해 결과를 꺼내는 구조다. 설문은 정량 항목(나이·주거·가족·가용 시간)과 자유 서술을 함께 받되 **자유 서술을 적극 유도**하고, LLM이 이를 분석해 추천한다. **나이는 정량 항목으로 수집·사용한다 (D-014 번복)** — 단 나이만으로 판단하지 않고 자유 서술과 함께 해석하며, 둘이 충돌하면 자유 서술을 우선한다.
- alternatives: D-014의 "나이 완전 제외" 안, 견종 추천과 보호견 추천에 각각 설문을 받는 안(초안의 순서)
- reason: 관심이 생긴 시점에 설문을 들이미는 것은 참여 장벽을 다시 세우는 일이다(설계 원칙 5). 온보딩에서 이미 받은 정보를 재사용하면 보호견 추천이 즉시 나온다. 나이는 정량 지표라 배제가 실질적으로 어렵고, 자유 서술 우선 규칙으로 편견 리스크를 관리하는 편이 낫다.
- evidence: `PRD.md` §2 데모 기준, §3, §4.1 온보딩, §4.3
- tradeoff: 온보딩 설문이 길어지면 초기 이탈이 커진다. 자유 서술 입력을 유도하되 최소 분량을 과하게 요구하지 않도록 UI에서 조절해야 한다. 또 여건이 바뀐 유저를 위해 설문 수정 경로가 필요하다.
- owner: 팀
- status: active

## D-018 — 사용자 위치를 수집하지 않는다 (GPS 기반 추천 철회)

- date: 2026-07-21
- decision: GPS 기반 추천 기능을 넣지 않는다. 사용자 위치 정보를 수집·저장하지 않으며, 위치 권한을 요청하지 않는다. 필요한 위치 정보는 보호소 쪽 지역(시·군·구) 하나뿐이고, 이는 추천 카드에 표시되는 정보일 뿐 추천 순위를 만드는 입력이 아니다. 지역으로 좁혀 보려는 사용자를 위해 직접 고르는 지역 필터만 선택 사항으로 둔다.
- alternatives: GPS로 가까운 보호소·봉사·긴급 후원 대상을 추천하는 안 (7/21 회의 초안 및 PRD v1.0 §4.3)
- reason: 온보딩에서 GPS 권한 요청은 그 자체로 이탈 지점이다. 위치정보는 별도 동의·보관 의무가 따르는 민감 정보이고, 10~20대를 포함한 전 연령 서비스에서 그 부담을 질 이유가 없다. 보호소 위치는 동물 안전과 직결되어 어차피 시·군·구까지만 공개하므로 정밀 좌표가 필요한 기능 자체가 없다.
- evidence: `PRD.md` §2 데모 기준, §4 루프 다이어그램, §4.3 "사용자 위치는 수집하지 않는다"
- tradeoff: "집 근처 보호소"라는 즉각적인 행동 유인이 약해진다. 참여 퍼널의 보호소 방문·봉사 단계에서 거리 판단은 사용자에게 맡기고, 지역 필터와 카드의 지역 표시로 보완한다.

## D-019 — 보호견 데이터 1차 소스를 서울 vPetInfo로 바꾼다 (§6.4 국가 API 전제 대체)

- date: 2026-07-22
- decision: 보호견 추천 카드의 1차 데이터 소스를 **서울 열린데이터광장 `vPetInfo`**(서울동물복지지원센터 반려동물 입양 정보)로 한다. 국가동물보호정보시스템 구조동물 API는 1차 소스에서 내리고, 전국 확장 시의 경로로만 남긴다.

## D-020 — LLM 프로바이더를 OpenAI로 시작하고, 호출부를 어댑터로 분리한다

- evidence: `11-backend/supabase/functions/_shared/llm.ts` (openAI / anthropic 어댑터, `fromEnv` 선택), 실제 호출 검증 `tests/e2e_analysis.ts`·`tests/e2e_recommend.ts`

## D-021 — 캐릭터견 견종 후보에 보더콜리를 항상 포함한다

- date: 2026-07-22
- decision: AI가 추천하는 견종 3개 중 하나는 **항상 보더콜리**로 고정한다. 고정 목록은 코드가 아니라 `config.breeds.pinned`에 두고, LLM 프롬프트에 지시하는 동시에 응답 검증에서도 강제한다.
- alternatives: 고정 없이 16종 중 자유 추천, 견종 목록 자체를 에셋 보유분으로 축소
- reason: 캐릭터견은 3D로 렌더되는데 현재 준비된 에셋이 보더콜리뿐이다. 고정하지 않으면 사용자가 에셋 없는 견종을 골라 캐릭터 생성이 깨질 수 있다. 견종 목록 자체를 1종으로 줄이면 "AI가 3개를 추천하고 유저가 고른다"(§4.1)는 온보딩 설계가 무너지므로, 목록은 16종을 유지하고 한 자리만 고정한다.
- evidence: `11-backend/supabase/migrations/0006_breeds.sql` (`pinned`), `_shared/analysis.ts` 검증, `tests/e2e_analysis.ts` — 여건이 상반된 두 사용자 모두 결과에 보더콜리 포함 확인
- tradeoff: 여건상 보더콜리가 적합하지 않은 사용자에게도 후보로 노출된다. 프롬프트에서 "억지로 맞추지 말고 감안할 점을 정직하게 쓰라"고 지시해 완화했으나, 추천 정확도는 일부 희생된다. **에셋이 늘어나면 `pinned` 배열을 비우는 것으로 즉시 해제된다.**

## D-022 — 기본 재화의 명칭을 "포인트"에서 "뼈다귀"로 통일 *(브랜치에서는 D-019로 기록됐으나 번호 충돌로 재부여)*

- date: 2026-07-22
- decision: 기본 재화를 **뼈다귀**로 부른다. 문서·게임 UI·와이어프레임·발표 자료 전부 해당된다. 재화 3종 구성(발바닥·뼈다귀·육포)과 §5.2의 단방향 전환 규칙은 그대로 유지하며, 바뀌는 것은 명칭과 표기(`P 12,400` → `🦴 12,400`)뿐이다. D-010에서 "포인트"로 정한 명칭을 대체한다.
- alternatives: 포인트 유지, MG1만 뼈다귀로 부르고 나머지는 포인트 유지
- reason: 포인트는 추상적인 숫자라 유저가 "무엇을 얼마나 얻었는지"를 그 자리에서 이해하기 어렵다. MG1의 보상 규칙을 확정하면서 *판에서 모은 뼈다귀 블록이 그대로 재화가 된다*는 구조를 잡았는데(mini-game-1-prd.md §4), 이때 획득물과 재화의 이름이 같아야 환산 설명 없이 보상이 읽힌다. 미니게임만 다르게 부르면 같은 재화를 화면마다 다른 이름으로 부르는 셈이라 전 서비스를 통일한다.
- evidence: `mini-game-1-prd.md` §4.1 보상 규칙, `PRD.md` §5.1·부록 A, `09-wireframes/` 전 화면 HUD 표기
- tradeoff: 과금 재화 "육포"와 같은 먹거리 계열이라 아이콘·색으로 구분이 필요하다. 뼈다귀는 🦴(아이보리), 육포는 갈색 계열로 대비를 유지한다.
- supersedes: D-010의 명칭 부분 (재화 3종 구성·전환 규칙은 유효)
